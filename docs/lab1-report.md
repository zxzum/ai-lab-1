# Отчёт по лабораторной работе № 1
## «Telegram-бот с языковой моделью»

- **Дисциплина:** Технологии искусственного интеллекта в разработке программного обеспечения
- **Тема:** Интеграция Telegram-бота с LLM, управление контекстом диалога и анализ параметров генерации
- **Ветка разработки:** `feature/student-assistant`
- **Тег сдаваемого состояния:** `lab1`

---

## 1. Цель работы и выбранный провайдер модели

**Цель работы:**
Освоить интеграцию Telegram-бота с большой языковой моделью через OpenAI-совместимый API, реализовать управляемый контекст диалога нескольких пользователей с разграничением ответственности в коде, разработать системные инструкции для трёх режимов работы (включая few-shot подход), исследовать влияние параметра `temperature` на вариативность ответов и покрыть решение автоматическими тестами без обращения к реальному API.

**Выбранный провайдер и модель:**
- **Провайдер:** OpenRouter API (`https://openrouter.ai/api/v1`)
- **Модель:** `google/gemini-2.5-flash-lite` (наиболее экономичная быстрая текстовая модель с поддержкой системных инструкций и изменения параметра `temperature`, стоимость ~$0.10 за 1 млн входных токенов; в качестве бесплатной альтернативы поддерживается `nvidia/nemotron-3.5-lightning:free`).
- **Версия API:** `/v1/chat/completions`.

## 2. Схема прохождения сообщения через приложение

Архитектура бота строго разграничивает Telegram-интерфейс, хранилище данных, логику контекста и клиент языковой модели:

```text
[Telegram] 
    │
    ▼ (Update: Message)
[aiogram Router: chat] ────(Проверка: только private чаты)
    │
    ▼
[StorageRepository] ───────(Чтение настроек: mode, temperature)
    │
    ▼
[StorageRepository] ───────(Загрузка скользящего окна истории: max_messages, max_chars)
    │
    ▼
[PromptBuilder] ───────────(Системный промпт активного режима + история + текущий запрос)
    │
    ▼
[ChatActionSender] ────────(Отправка действия "печатает...")
    │
    ▼
[LLMClient] ───────────────(HTTP POST /v1/chat/completions через aiohttp с таймаутом)
    │
    ├── Ошибка (Timeout/4xx/5xx) ──► Отправка безопасного сообщения на русском языке
    │                                (сообщение ассистента НЕ сохраняется в историю)
    │
    ▼ Успех
[StorageRepository] ───────(Сохранение user и assistant сообщений в PostgreSQL)
    │
    ▼
[split_message] ───────────(Разбиение на блоки <= 4096 символов при необходимости)
    │
    ▼
[Telegram] ────────────────(Отправка частей ответа в строгом хронологическом порядке)
```

**Разделение модулей:**
- `app/config.py` — считывание параметров, строгая валидация, защита секретов.
- `app/db.py` и `app/storage/repository.py` — подключение к PostgreSQL и изоляция SQL-запросов.
- `app/llm/client.py` — асинхронный HTTP-клиент к LLM API с логированием безопасных идентификаторов и времени.
- `app/llm/prompts.py` — системные инструкции режимов.
- `app/handlers/commands.py` — обработчики команд `/start`, `/study`, `/translate`, `/code_review`, `/settings`, `/reset`.
- `app/handlers/chat.py` — обработчик текстовых сообщений пользователя.
- `app/utils/text.py` — утилита безопасного разбиения длинного текста.

## 3. Описание хранения и ограничения контекста

### Хранение в PostgreSQL
Данные диалогов и пользовательские параметры сохраняются в реляционной базе данных PostgreSQL:
1. Таблица `user_settings`:
   - `user_id BIGINT PRIMARY KEY` — идентификатор пользователя в Telegram.
   - `mode VARCHAR(32) NOT NULL DEFAULT 'study'` — активный режим диалога.
   - `temperature REAL NOT NULL DEFAULT 0.7` — выбранная температура генерации.
   - `updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`.
2. Таблица `dialog_messages`:
   - `id BIGSERIAL PRIMARY KEY` — сквозной идентификатор сообщения.
   - `user_id BIGINT NOT NULL` — владелец сообщения (обеспечивает полную изоляцию пользователей).
   - `role VARCHAR(16) NOT NULL` — роль (`user` или `assistant`).
   - `content TEXT NOT NULL` — текст сообщения.
   - `mode VARCHAR(32) NOT NULL` — режим, в котором состоялся диалог.
   - `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`.
   - Индекс: `idx_dialog_messages_user_mode_created (user_id, mode, created_at ASC)`.

### Стратегия ограничения контекста
Контекстное окно ограничено одновременно двумя параметрами конфигурации:
- `MAX_HISTORY_MESSAGES` (по умолчанию `10`) — максимальное количество сообщений из предыстории;
- `MAX_HISTORY_CHARS` (по умолчанию `4000`) — оценочный суммарный объём символов истории диалога.

**Алгоритм сокращения (скользящее окно):**
1. Из базы выбираются последние `N` сообщений текущего пользователя и режима (`ORDER BY created_at DESC LIMIT max_messages`).
2. Начиная с самых свежих сообщений, накапливается суммарная длина строк. Если добавление очередного сообщения превышает `max_chars`, выборка прекращается.
3. Отобранные сообщения разворачиваются в хронологический порядок (от старых к новым).
4. К отобранной истории добавляется системная инструкция активного режима в начале и текущий запрос пользователя в конце:
   `[system_instruction] + [history] + [current_user_message]`.
5. Текущий запрос пользователя и системная инструкция **никогда не отбрасываются**.

## 4. Тексты трёх системных инструкций и разбор их элементов

Инструкции составлены на основе учебной мнемоники **R.C.T.F.** (Role, Context, Task, Format):

### 1. Режим `/study` (Объяснение учебных тем по программированию)
```text
[Role]
Ты — терпеливый преподаватель-наставник по программированию и компьютерным наукам.

[Context]
Студент изучает основы алгоритмов, структур данных, программирования и архитектуры ПО.

[Task]
Твоя задача — понятно объяснить заданную тему, теорию или концепт. Не пиши сразу готовых громоздких решений, объясняй логику по шагам, стимулируя мышление студента.

[Constraints]
1. Отвечай на русском языке.
2. Избегай заумного академического жаргона без пояснения сути.
3. Код приводи на Python, если студент явно не просил другой язык.
4. В конце ответа обязательно задай один короткий наводящий вопрос для самопроверки.

[Format]
Структурируй ответ по блокам:
1. 💡 Суть концепции простыми словами
2. 💻 Наглядный пример кода с пояснениями
3. ⚠️ Типичные ошибки новичков
4. ❓ Вопрос для самопроверки
```
*Разбор:* Четко задана педагогическая роль наставника, контекст обучения в вузе, задача пошагового объяснения без «медвежьей услуги» в виде готовых домашек, а также детерминированный формат с обязательным вопросом на понимание.

### 2. Режим `/translate` (Технический переводчик с Few-Shot примерами)
```text
[Role]
Ты — профессиональный технический и литературный переводчик.

[Context]
Студент отправляет текст и просит перевести его на целевой язык.

[Task]
Твоя задача — выполнить точный перевод текста на запрошенный язык с сохранением регистра, разметки Markdown, названий переменных и кода.

[Constraints]
1. Не добавляй лишних приветствий и вводных слов в ответ.
2. Имена переменных, ключевые слова языков программирования и фрагменты кода не переводи.
3. Пограничный случай: если пользователь прислал текст, но НЕ указал целевой язык, вежливо попроси уточнить язык перевода.

[Examples]
Пример 1 (Технический перевод на английский):
Пользователь: Переведи на английский: Стек — это структура данных (LIFO).
Ассистент: A stack is a data structure that operates on the LIFO principle.

Пример 2 (Пограничный случай — язык не указан):
Пользователь: Привет! Как подключить базу данных?
Ассистент: Укажите, на какой язык перевести текст (английский, немецкий).

Пример 3 (Сохранение кода и терминов):
Пользователь: Переведи: Ensure `user_id` is an int before `get_user()`.
Ассистент: Убедитесь, что `user_id` является int перед `get_user()`.
```
*Разбор:* Применяет подход few-shot с тремя парами «вход-выход», включая важный пограничный случай (пользователь не указал язык) и защиту программных идентификаторов от перевода.

### 3. Режим `/code_review` (Собственный режим: ревью студенческого кода)
```text
[Role]
Ты — внимательный старший разработчик и код-ревьюер (Tech Lead).

[Context]
Студент отправляет фрагмент кода на ревью для поиска ошибок и улучшения.

[Task]
Твоя задача — конструктивно проанализировать код, выявить логические и синтаксические ошибки, проверить граничные случаи, оценить соответствие стилю PEP 8 и читаемость, предложить исправленный вариант.

[Constraints]
1. Отвечай конструктивно, вежливо и доброжелательно на русском языке.
2. Обязательно выдели критические ошибки (деление на ноль, границы).
3. Если код идеален, похвали студента и объясни, почему решение удачное.

[Format]
Структурируй ответ:
1. 🔍 Что делает код (кратко)
2. ⚠️ Замечания и найденные баги
3. 💡 Рекомендации по чистоте и стилю кода
4. ✨ Улучшенный вариант кода с пояснениями
```
*Разбор:* Решает принципиально отличающуюся прикладную задачу анализа исходного кода, заставляет модель проверять пограничные случаи и структурировать критику конструктивно.

## 6. Сравнение исходной и улучшенной инструкции

- **Тестируемый запрос:** `«Переведи: Ensure user_id is an integer before saving.»`
- **Исходная (намеренно неполная) инструкция:**
  > *"Ты бот-переводчик. Переводи всё, что присылает пользователь."*
  - **Ответ модели на исходную инструкцию:**
    > *"Привет! Конечно, вот перевод твоего предложения: Убедитесь, что идентификатор пользователя является целым числом перед сохранением."*
  - **Проблемы исходной инструкции:**
    1. Лишнее приветствие и вводный шум («Привет! Конечно, вот перевод...»).
    2. Перевод технического идентификатора `user_id` как «идентификатор пользователя», что недопустимо при переводе кода и документации.
    3. Отсутствие обработки ситуации, когда язык не указан.

- **Улучшенная инструкция (с R.C.T.F. и Few-Shot):**
  > Системный промпт режима `/translate` (см. раздел 4).
  - **Ответ модели на улучшенную инструкцию:**
    > *"Убедитесь, что `user_id` является целым числом перед сохранением."*
  - **Результат улучшения:**
    1. Исключены лишние приветствия и вежливые префиксы.
    2. Сохранён регистр и программное оформление переменной `` `user_id` ``.
    3. Перевод краток, точен и готов к использованию в технической документации.

## 8. Известные ограничения и нерешённые пограничные случаи

1. **Входное сообщение, превышающее лимит контекста:** Если пользователь пришлет в одном сообщении текст длиной более 100 000 символов, он превысит лимит контекстного окна модели ещё до добавления системного промпта. В продакшене требуется предварительно валидировать длину входящего пользовательского сообщения (например, не более 10 000 символов) и возвращать предупреждение.
2. **Частичный сбой при отправке серии сообщений:** Если ответ модели длиннее 4096 символов был разбит на 3 части, и Telegram API вернул сетевую ошибку на 2-й части, пользователь получит неполный ответ. Решением может быть сохранение статуса отправки в очереди сообщений.

## 9. Декларация использования AI-инструментов

При разработке решения применялся AI-ассистент для проектирования архитектуры и генерации тестовых сценариев.

**Пример отклонённого / исправленного предложения AI-инструмента:**
1. **Отклонено:** Первоначально AI-ассистент предложил установить стороннюю библиотеку `openai` для взаимодействия с API. Это предложение было **отклонено**, так как в проекте уже присутствует и зафиксирован в `constraints.txt` легковесный асинхронный HTTP-клиент `aiohttp`. Написание прямого клиента к эндпоинту `/chat/completions` через `aiohttp` сделало код намного более прозрачным для понимания первокурсником и исключило лишние тяжелые транзитивные зависимости.
2. **Исправлено:** Тесты жизненного цикла использовали недостаточно точный mock для `pool.acquire()`, из-за чего реализация `init_db` проглатывала `TypeError`. Mock был исправлен, а обработка ошибки удалена, чтобы сбой создания схемы останавливал запуск приложения.
